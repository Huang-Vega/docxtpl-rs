# ADR-005：P4 富内容值的类型化上下文与图片注册表

日期：2026-09-25
状态：已接受
阶段：P4（RichText 与图片）

## 背景

P2/P3 的渲染上下文是纯 JSON（`serde_json::Value`），因为上游 `tpl.render(context)`
对模板内变量只做文本替换。P4 引入三类上游"类型化值"：`RichText`/`RichTextParagraph`
（构造 `w:r`/`w:p` XML 片段）、`Listing`（转义文本，复用既有 resolve_listing）、
`InlineImage`（渲染时读取图片字节、写 media part、分配 rId、注入 `wp:inline`）。
它们无法用 JSON 表达，且 `InlineImage` 具有跨 part 的包级副作用。

## 探针钉死的上游事实（docxtpl 0.20.2 + python-docx 1.2.0 + lxml 6.1.1）

1. **`InlineImage.__str__` 输出是 python-docx `BaseOxmlElement.xml`**
   （`etree.tostring(..., pretty_print=True)`）：`wp:inline` 树无空白，输出时
   按 2 空格/层 pretty 缩进，根闭合后带一个换行；外层包装为拆 run 字符串
   `</w:t></w:r><w:r><w:drawing>…</w:drawing></w:r><w:r><w:t xml:space="preserve">`。
2. **宿主序列化裁剪冗余命名空间声明**：字符串注入的 `wp:inline` 自带
   `wp/a/pic/r` 四声明；recover 解析 + lxml 序列化后，与祖先轴上
   "同前缀同 URI"绑定重复的声明被裁（探针 A/B/C/D 确认：不同 URI 保留、
   兄弟不参与、默认前缀同样处理），剩余声明保持原相对顺序——最终只剩
   `xmlns:a`、`xmlns:pic`。
3. **shape_id 语义**：`StoryPart.next_id` 对**渲染开始前的原始 document 树**
   取 `//@id`（数字化）max+1；字符串渲染阶段树不更新，因此同一文档内多张图
   的 `wp:docPr` id/name 相同（如都是 `id="1" name="Picture 1"`）；唯一性由
   渲染后的 `fix_docpr_ids`（1001 起重编号）修复。`pic:cNvPr` 恒 `id="0"`，
   name 为图片文件 basename。
4. **rId 分配**：`Relationships._next_rId` 从 rId1 起回填第一个空洞（非
   max+1）；image 关系按需创建（`relate_to`，命中同 reltype+target 复用），
   hyperlink（anchor）外链关系尾插追加。图片 part 按 sha1 去重，
   `word/media/imageN.ext` 编号同样取第一个空洞。
5. **尺寸**：`EMU = int((px/dpi)*914400)`（f64 除→乘→截断）；仅给宽或高时
   银行家舍入保持纵横比（`round`），两者都给时原样使用不做约束。
6. **rels 与 [Content_Types].xml 在 python-docx 保存时整体重建**：rels 为
   `<Relationships xmlns=…>`（属性序 Id/Type/Target/[TargetMode]），
   Content Types 为 Default（按扩展名 sorted）+ Override（按 partname sorted），
   均带 lxml 单引号声明 + 换行。P0–P3 期间这两类 part 因内容未变，原字节
   恰与重建结果一致；P4 一旦新增关系/图片就必须按该格式重建。

## 决策

1. **新增 `docxtpl-rich` crate**（对应项目文档 §5 组件表 P4–P6 行）：
   - `RichText`/`RichTextParagraph`/`Listing`/`InlineImage` 类型，`to_xml()`
     与上游逐字节对齐（含 `html.escape` 语义：仅转义 `& < >`）。
   - `Image`：png/jpeg/gif/bmp/tiff 头解析（sha1、px、dpi、ext、content type），
     按探针与 python-docx 源码逐字段复刻。
   - `RenderValue`：`Json(..)` | `RichText(..)` | `RichTextParagraph(..)` |
     `Listing(..)` | `InlineImage(..)`；`RenderContext` 为有序 map。
   - minijinja 桥接：富值包装为 `ObjectRepr::Plain` 自定义对象，实现
     `Object::render` 等价上游 `__str__`（`{{ v }}` 直接展开 XML）。
     autoescape=True 时上游经 `__html__` 仍不转义；本侧 render 输出是否被
     minijinja 转义未在 oracle 范围内（fixture 全部 autoescape=False），
     该差异登记为 P4 已知限制（见 compatibility.md §5）。
2. **渲染管线泛化**（docxtpl-template）：`render_document_xml` 增加
   `RenderContext` 变体与 `ImageRegistry` 参数；`shape_id` 在渲染前从原始
   `word/document.xml` 计算（一次性，全部 InlineImage 共享）；
   `render_xml`/`InlineImage` 需要的包级服务全部经
   `ImageRegistry::resolve(..) -> {blip_rid, hyperlink_rid, filename, cx, cy,
   shape_id}` 交付，模板 crate 不依赖 OPC。
3. **门面实现 `ImageRegistry`**（docxtpl-rs）：作用于 `Package`——
   sha1 去重、media part 命名、rId 空洞分配、`[Content_Types].xml` 与
   document rels 的 python-docx 风格重建；渲染完成后把 media part 字节
   （原样）写入包。
4. **docxtpl-xml 序列化器增加 lxml 裁剪语义**：输出元素时跳过"祖先轴上
   同前缀同 URI"的自有 nsdecls，其余按原顺序保留（探针 A–D 规则）。
   该行为对既有 golden 无影响（其子树无冗余声明），48 recover golden
   必须全绿回归。
5. **fixture 演进**：`generate.py` 产出 `p4_*` 模板与图片样本（自造
   2×1 PNG、4×2 300dpi JPEG 等，可复现字节）；`manifest.json` 增加
   `context_kind`（`json`|`python`）；`runner.py` 对 python 上下文加载
   `build_context(tpl)`；`dump_stages.py` 同步输出 p4 stages golden。
   不允许修改既有 fixture/golden。

## 影响

- 公开 API：新增 `DocxTemplate::render_ctx(&RenderContext, &RenderOptions)`；
  既有 `render(&JsonValue, ..)` 保持不变（内部转 RenderContext）。
- CLI：`docxtpl render` 增补 `--image <name>=<path>[:WxH]` 之类的图片注入
  参数推迟到独立评审，P4 以 API 为主（上游 CLI 行为不存在，避免发明行为）。
- 兼容性：P4 差分口径不变（逐字节 part + c14n）；新增 p4_* fixture 全部
  纳入 compatibility.md §7。
